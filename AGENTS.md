# Project engineering rules

- For proxied Google Live Browse sessions, keep a no-op Playwright route enabled because Chromium proxy-auth redirects can otherwise hang.
- Treat recorder status polling as failed only after five consecutive misses, then persist the failure so sessions cannot remain falsely active.
- Launch recorder Chromium with handleSIGTERM/SIGINT/SIGHUP false, because Playwright otherwise kills live sessions during blue-green drain.
- Pinterest Live Browse sessions load the official Google Translate extension via launchPersistentContext (--load-extension, worker/recorder/extensions/google-translate) because extensions cannot load in ephemeral browser contexts; TRANSLATE_EXTENSION=off disables it.
- Social credentials, cookies, and persistent browser profiles are isolated by workflow account and platform; never inherit or copy them by country, proxy, tenant, or sibling workflow, because that creates cross-account identity conflicts.
- Recorder and executor profiles live on host-backed persistent volumes and use the real Linux browser identity; locale and timezone follow proxy geography, preventing a fresh-device signal and OS contradictions.
- STT raw audio and reference texts stay on the VPS corpus volume (STT_CORPUS_HOST_DIR → /stt-corpus); stt_media_fetch defaults to local storage and stt_calibrate returns only small accuracy results, because cloud storage of the corpus is too costly.
- Membership archives (membership_archive / membership_transcribe) keep media, transcripts and manifest.json only on the VPS volume (MEMBERSHIP_HOST_DIR → /membership); only small status results and text chunks for structuring leave the VPS, because the content is the owner's private paid material.
- The Brain reaches the VPS file server only via its HTTPS hostname (vaultFileBaseUrl), never a bare IP, because Cloudflare Workers reject outbound fetches to raw IPs with 403.
- worker/deploy.sh re-execs itself once right after git pull, because bash reads scripts lazily and a pull that rewrites deploy.sh corrupts the running instance.
- Subject factory packages use a separate versioned HMAC-authorized task with a fixed tenant grant, host/file allowlists and exclusive checksum-verified finalization outside the archive; receipt never executes installers, because downloaded code requires independent review and deployment authorization.
- Subject factory installs only via infra/subject-factory/safe-install.sh (pre-validated tar, new versioned release dir, reviewed unit) gated by APPROVED_MANIFEST; the package's own install.sh is never run, because it extracts unchecked as root.
- Subject factory diagnostics use a host timer and the authenticated worker heartbeat with fixed unit/file allowlists and bounded redacted tails; never expose arbitrary commands or public install logs, because deployment completion does not prove production started.
- Subject factory runtime corrections are narrow, fail-closed transformations mounted read-only beside the approved image; staging must live inside the same bind mount as the archive (hard-link finalization fails across mounts with EXDEV); Chromium HOME and XDG directories use the writable /tmp mount because crashpad cannot launch on a read-only home; deploy resumes a failed installed service once per correction version without resetting receipts, because archive immutability and restart safety must remain intact.
- Completed subject-factory receipts prevent deploy-triggered restart; missing auto-removed containers are successful stops only when the Docker daemon can list containers, because completion must not cause regeneration or hide daemon failure.
- The standalone video-factory module uses host-local SQLite state, outbound signed KyLogic commands, immutable data recipes and a separately reviewed renderer; install.sh only stages, and the long-running manager is activated solely by activate-manager.sh, which fails closed without the machine secret, the reviewed renderer, finished continuation preparation and a stopped legacy producer, and never restarts during an active render.
- Continuation preparation and manager activation run sequentially in the same background systemd job, with activation conditional on successful preparation; deploy only activates directly when preparation is already finished, so first-update startup needs no second deploy and failures stay closed.
- Recipe fonts are optional checksum-declared data loaded by an additive digest-pinned renderer; partial IELTS continuations require disjoint completed/rendered/justified-blocked language coverage, and command failures persist to the outbox, so missing glyphs or rejected recipes cannot silently trigger production or hide failure.
- Legacy completed receipts may use the reviewed brain-archive read alias only for verification; all new outputs remain under the factory archive root, and bounded missing-file keys plus continuation receipts travel through protected diagnostics so failures can be located without moving masters.
- Provision the factory machine secret only to the authenticated worker as RSA-OAEP ciphertext for an ephemeral host key; the root-only helper atomically writes a private host file without logging credentials or activating production, because cloud secrets do not automatically reach the VPS.
- Prepare missing factory host tools through the fixed ffmpeg/openssl package allowlist before staging; never upgrade the whole host or start production, because executor-container dependencies are not host dependencies.
- Explicit owner-authorized trial deployments use a checksum-bound media package, reviewed source-built immutable renderer image and a one-shot host service with no remote claim; existing producers block takeover, preserving archive and state. Host manager paths must remain visible to Docker bind mounts, so do not isolate its temporary namespace.
- Video-factory render failures persist a bounded local cause (exception, code line, renderer stderr tail) to last-render-failure.json and the protected diagnostics also read the state DB read-only, because generic failure codes alone made trial failures undiagnosable.
- Verified recipe files and their mount-local directories are made read-only/readable for the renderer before ingestion completes and before rendering existing recipes; never change archive permissions or host ancestors, because older root-private inputs otherwise fail for the unprivileged renderer.
- New exam-profile renderers (e.g. exam-renderer for Cambridge) are ported onto the current reviewed renderer source and installed as additional digest-pinned renderer entries via their own prepare script, and each must be added to the fixed name→scene allowlist in activate-manager.sh; never adopt an uploaded renderer wholesale, because older bases silently revert path-safety, font and duration fixes and unlisted entries block activation.
- A pinned renderer entry may be re-registered with a new image digest only when the previously pinned image no longer exists in Docker (recovery, not replacement); if the old image still exists, a differing entry stays an immutable_renderer_conflict, because otherwise a deploy could silently swap a reviewed renderer.
- Caption-corrected exam releases have independent checksum-pinned source directories, prepare scripts and fixed name/scene grants; port only caption changes onto the reviewed renderer so font, path and duration protections and all existing renderer assignments stay intact.
- Universal exam recipes use an additive version-two contract and independent SQLite job tables; legacy validators, receipts and pinned renderers retain their semantics, because changing old recipes would invalidate approved outputs.
- Universal preview jobs terminate without MP4 publication; full outputs require per-frame layout evidence, media QA and no-clobber versioned publication, because preview authorization is not production authorization.
- Universal tight-cut rounds frozen-and-silent gaps inward to frame boundaries, preserves narration/CTA/outro windows and remaps caption times and measured frame evidence before final decode and duration QA, because shortening media without remapping invalidates synchronization.
- Factory HTTP diagnostics retain only operation/status and allowlisted error codes from signature-verified responses; log local phases without response bodies, headers or free text, because remote failures can contain secrets or untrusted content.
- Video-factory activations are serialized with a host flock and clear the unit's failed/start-limit state before a planned restart, because several renderer preparations finishing in one deploy otherwise exhaust StartLimitBurst and leave the manager stopped.
